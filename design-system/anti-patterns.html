Anti-patterns gallery

Compact do/don't pairs covering the most common Sui-diagram compliance slips. Pair these with the deep transactions.mdx anti-example for a full picture of what to avoid.

1 · Off-palette arrow color

✗ Avoid
✓ Correct

Red arrows leak error semantics into a routine call , and readers infer something is failing. Sui Blue is the canonical connector color; any on-palette gray works for de-emphasis. Reserve non-palette colors for nothing.

2 · Rounded rectangles

✗ Avoid
✓ Correct

Sui's diagram language uses sharp corners only. Pill and rounded-rect shapes pull in consumer-app/marketing UI semantics the diagrams should stay clear of. The token --sui-node-radius is set to 0 on purpose.

3 · Unlabeled operator boundary

✗ Avoid
✓ Correct

Every boundary rectangle carries a sentence-case label at top-left, outside the rect. An unlabeled boundary leaves the reader guessing what the grouping means: operator zone, trust boundary, or deployment unit. A label answers that in two words.

4 · Ellipses for primary nodes

✗ Avoid
✓ Correct

The ellipse is reserved for operator boundaries / zones, never for systems or containers. A primary node is always a filled rectangle; an actor is an outline-only rectangle; an external system is a dashed rectangle. One shape per element type, no swaps.

5 · Mixed C4 levels (embedding components inside an architecture)

✗ Avoid
✓ Correct (two companion diagrams)

Embedding three components inside the SUI FULL NODE container forces a reader to absorb two abstraction levels at once. Split into a Level 2 architecture (containers + their peers) and a Level 3 component (insides of one container). Cross- reference in the caption with the v-suffixed filename. The Level 2 diagram stays focused on data flow, the Level 3 stays focused on internal structure.
